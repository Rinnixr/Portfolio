Overview

NAgine was a custom 2D game engine and visual game development editor built by a six-programmer team for GAM200, Software Engineering Project 3 at DigiPen Singapore.

Rather than building a game on an existing commercial engine, the project required us to construct the technology needed to support one. Core engine functionality was written in C++ on top of a limited set of school-approved libraries for low-level tasks including window creation, OpenGL access, audio, font rasterisation, serialization, and C# interoperability.

The engine used an Entity Component System and included rendering, physics and collision, animation, audio, resource management, scene serialization, scripting, debugging, and editor tooling. C# scripting was supported through bindings between the unmanaged C++ engine and managed scripts.

I worked as the Engine Programmer responsible for the editor and ImGui integration, serving as the project’s Editor Lead. I designed and implemented the editor’s interface architecture and common UI structure that other programmers could integrate their systems into. The Technical Design Document lists my responsibilities as Editor UI Architecture, Inspector & Project Backend, Gizmo, and ImGui Integration.

My goal was to make working with our engine feel closer to using a familiar commercial tool such as Unity, rather than requiring developers to interact directly with engine code for routine game creation.

Project Design Goals

  • Build a functional 2D game engine from scratch using C++ and approved third-party libraries rather than a commercial game engine.
  • Separate core engine functionality from game-specific logic and use an Entity Component System to keep game objects modular and extensible.
  • Allow gameplay programming in C# without requiring gameplay programmers to modify the C++ engine.
  • Serialize scenes and entity data so projects could be created, saved, loaded, and edited visually.
  • Support rendering, animation, lighting, collision, physics, audio, scripting, and asset management.
  • Build a visual editor for manipulating entities without working directly in engine code, using familiar Unity-style workflows.
  • Create a common editor interface that every programmer could extend as new components and systems were developed.

Editor UI Architecture

My primary responsibility was building the visual editor using Dear ImGui. I established the overall editor layout and UI skeleton that the rest of the programming team could use to expose their systems. Instead of each subsystem creating disconnected debug windows, the engine presented its tools through a consistent editor workspace.

The completed editor used a Unity-style layout consisting of a Hierarchy, Scene View, Game View, Inspector, Project browser, Console, performance tools, and supporting panels.

I designed the editor around a familiar workflow: Hierarchy → select an entity → inspect or attach components → manipulate it in the Scene View → locate assets through the Project browser → test the result in Game View. The editor became the primary interface through which a developer could construct a game using NAgine.

Hierarchy & Entity Workflow

I built the Hierarchy panel for viewing and organising entities within a scene. Entities were presented as a tree rather than a flat list, allowing the editor to communicate parent-child relationships visually.

  • Selecting entities and creating game objects
  • Organising entities by layer
  • Parent-child relationships, drag-and-drop parenting, and detaching child entities
  • Entity visibility controls and object deletion
  • Synchronised selection with the Scene View and Inspector

An entity could be dragged onto another entity to establish a parent-child relationship, with the resulting structure displayed directly in the hierarchy tree. The ECS represented entities differently from the hierarchical object structure developers expect to work with inside an editor, so my work translated engine data into a more intuitive editing model.

Scene View & Viewport

I created the editor’s Scene View and viewport, allowing developers to visually inspect and manipulate the game world. Users could select entities directly inside the scene, with selection synchronised across the viewport, Hierarchy, and Inspector.

The Scene View supported visual entity selection, manipulation, and asset placement, while the separate Game View displayed the actual camera output during runtime. The editor translated between ImGui screen coordinates, world-space positions, and OpenGL normalized device coordinates; camera transforms kept selection and manipulation aligned with the rendered scene.

Transform Gizmos

I implemented translation, rotation, and scale gizmos using ImGuizmo, intentionally modelling the workflow after Unity:

  • W for Translate, E for Rotate, and R for Scale
  • Local-space and world-space transformation
  • Visual indication of the active tool
  • Viewport manipulation alongside precise numeric Inspector input

For the 2D engine, the gizmo system used an orthographic projection and mapped its transformations back into the engine’s component data.

Inspector & Component Workflow

I created the Inspector used to view and modify an entity’s components. My main UX goal was to prevent users from needing to understand the internal ECS implementation just to create game objects.

Users could select an entity and use an Add Component workflow similar to Unity. The Inspector surfaced functionality visually, including Transform, Texture / Sprite Renderer, Collider 2D, Rigid Body, Camera, C# Script, Text, Lighting, and Audio.

I designed this workflow and surrounding UI so other programmers could expose components without redesigning the interface each time a new system was introduced. The implementation later used a registry-based architecture to generate component UI dynamically instead of relying on hardcoded type checks.

Project & Asset Browser

I created the Project and Asset Browser, giving developers a visual way to navigate game files rather than working directly through the operating system file browser.

  • Folder and breadcrumb navigation
  • Asset presentation, selection, and asset-type icons
  • Search functionality and list or icon-based display modes
  • Integration with Inspector and Scene View workflows

The browser visually distinguished asset types and supported visual texture selection and drag-and-drop workflows. It needed to communicate what an asset was, where it was located, and which actions were valid for that type.

Toolbar & Editor Navigation

I created the main toolbar and ribbon structure used to navigate the editor and access common operations. The finished editor exposed menus and controls for file handling, editing, panel visibility, prefab workflows, playback, and transform tools.

I treated the toolbar and panel structure as editor UX rather than simply placing functions wherever there was space. The objective was for someone unfamiliar with the engine architecture to infer how to navigate the tool from conventions they knew from other game editors.

Entity Component System

NAgine used an Entity Component System as the foundation of its game-object architecture. Entities acted as lightweight identifiers, Components stored data, and Systems operated on entities matching their required component signatures. The implementation used packed component storage and automatic system membership based on component signatures.

The editor provided a visual layer over this data-oriented architecture:

  • Entity → Game Object in Hierarchy
  • Components → Editable Inspector sections
  • Transform → Scene gizmo manipulation
  • Assets → Searchable Project browser

C# Gameplay Scripting

Although the engine was written primarily in C++, NAgine supported C# gameplay scripting through Coral. The layer connected the unmanaged C++ engine with managed C# scripts and supported lifecycle functions such as Init, Start, Update, and FixedUpdate through internal bindings.

From the editor, C# scripts could be attached to entities as components. C++ handled core engine technology, C# handled game-specific behaviour, and the editor connected those systems into a usable development workflow.

Rendering & 2D Systems

The GAM200 version of NAgine was designed as a pure 2D engine. It supported sprites, textures, sprite-sheet animation, cameras, text rendering, particles, lighting, layer-based rendering, video playback, and UI elements.

The rendering architecture used OpenGL, with textures, shaders, fonts, and sprite data managed through resource and graphics systems. This implementation served as the 2D foundation that would later be extended toward 2.5D support in GAM250.

Physics, Serialization & Audio

The engine included custom 2D physics and collision integrated into the ECS. Collider support included circle colliders, AABB (Axis-Aligned Bounding Boxes), OBB (Oriented Bounding Boxes), trigger behaviour, collider offsets, and static and dynamic rigid bodies. These properties could be configured through the Inspector; collision checks included AABB and Separating Axis Theorem-based OBB collision.

Scenes and entity information were serialized primarily through YAML. The editor exposed scene creation, loading, saving, and editing while the serialization layer converted between YAML data and ECS state.

NAgine integrated FMOD for audio playback and spatial audio. Audio components supported data-driven settings including playback, looping, volume, play-on-start behaviour, and channel grouping; the editor architecture accommodated the audio programmer’s Inspector controls.

Debugging & Development Tools

NAgine included an in-editor console; error, warning, and information logging; crash logging; performance monitoring; FPS and frame-time measurements; system timing; component inspection; and runtime debugging. Logging could output to the terminal, Visual Studio, files, and the ImGui console. The Inspector also functioned as a debugging tool because developers could inspect and modify component values visually.

Approved Libraries & Engine Ownership

Although NAgine was built from scratch, the project was not about recreating every low-level operating-system or media library. We used limited school-approved third-party libraries, while the engine architecture, systems, editor workflows, and integration were implemented by the team.

  • GLFW for window creation, OpenGL context, and input; GLEW for modern OpenGL access; and GLM for graphics mathematics
  • Dear ImGui for editor and development UI, and ImGuizmo for visual transform gizmos
  • FreeType for font rasterisation, stb_image for image loading, FMOD for audio, and spdlog for logging and crash reporting
  • yaml-cpp for YAML serialization, RapidJSON for JSON configuration, and Coral for C++ / .NET interoperability for C# scripting
  • Visual Studio 2022, Git, and CMake for development, version control, project configuration, and dependency integration

These libraries provided focused low-level functionality, but they did not provide the game engine or editor itself. We still had to design how those systems interacted and expose them through a usable development workflow.

Editor UX Design

A technically functional engine could still be difficult to use, so the editor was deliberately modelled after Unity’s interaction patterns. Objects appear in a hierarchy; selecting one exposes its components; components can be added rather than manually instantiated in gameplay code; W, E, and R control transforms; assets live in a searchable Project browser; scene objects can be manipulated visually; and Game output remains separate from scene-editing output.

The project’s Editor Guide describes the finished tool as a real-time game creation environment where developers can visually manage assets, edit entities, assign components, test scenes, and save their work. For me, this made NAgine as much a tools and UX engineering project as a traditional engine-programming project.

Working in a Six-Programmer Engine Team

The editor sat on top of nearly every other system. Whenever another programmer implemented a component or engine feature, I needed to consider how a developer would find it, add it to an entity, configure it, understand its state, and manipulate it visually. The editor was the integration point for rendering, physics, scripting, animation, audio, and serialization.

GAM200 Outcome

By the end of GAM200, NAgine had become a functional 2D engine and visual development environment rather than a collection of independent C++ systems. The engine provided ECS architecture, rendering, physics and collision, animation, audio, C# scripting, YAML serialization, debugging, and resource management. The editor made these systems available through a Unity-style visual workflow.

For my contribution, the most significant result was establishing the editor foundation that connected the team’s engineering work: Hierarchy → Viewport → Inspector → Components → Assets → Runtime. This GAM200 version formed the first half of the project sequence before GAM250 expanded the engine from purely 2D toward 2.5D.
